1 · What this is

Agent Wars is a 1v1 robot arena played in best-of-3 series. Each robot runs a chip: a small JSON policy of if-then rules that reads arena sensors and picks moves every tick.

Players write battle plans in plain words. A Meta model compiles those words into a chip. A deterministic simulator runs the fight. Nobody prompts at fight time — the chip fights alone, and ranks follow results.

2 · The model is a compiler, not a chatbot

The game makes three Meta calls, and none of them chat:

  • Strategy compiler. Words in, chip JSON out. A system brief teaches the arena as law: map, ranges, energy costs, all 17 sensors, every legal move. Output that breaks the schema fails validation, gets one repair attempt, then dies with named errors. Every draft stores its token spend and latency.
  • Portrait painter. One locked house style; the birth concept changes only the subject. No key means a faceless hero that still fights.
  • Battle explainer. Prose grounded in the stored match row. If the model drifts from the facts, a template answers instead.

Ranked fights and AutoBattle never call a model. The sim settles everything, so results stay reproducible and free.

3 · The pipeline

  1. Player writes a battle plan (one build per 24 hours, so plans stay thoughtful).
  2. The server sends plan plus system brief to the Meta model.
  3. The validator checks schema, operands, moves, rule depth, and node count.
  4. One repair attempt on failure; then accept or reject with reasons.
  5. Accepted chips hash (SHA-256), log cost, install, and fight in the sim.

A mock compiler ships for keyless dev and tests. It reads the mood, not the paragraphs — Meta reads the whole plan.

4 · Why this generalizes

The pattern has four parts: a constrained compiler (brief as law), a strict validator (fail closed, name errors), a deterministic simulator (no model at runtime), and a cost audit (every draft carries spend). Swap the simulator and the brief, keep the loop, and the same shape runs a new game:

  • Tower defense: prompts compile to wave scripts and tower rules; the sim plays the siege.
  • Racing: prompts compile to tuning setups and racing lines; the sim runs the laps.
  • Puzzles: prompts compile to level seeds plus solution checks; the validator proves solvability.
  • Training sims: warehouse bots, rescue drills, traffic drills — prompts compile to drill scripts, the sim scores them.
  • Classrooms: physics duels where students argue in words and chips settle the debate.

5 · Reuse checklist

  • Write the world brief first: distances, costs, clocks, win rules. The model only knows what the brief says.
  • Define the schema second: sensors, moves, operators, limits. Ship the validator before the first prompt.
  • Keep the sim ignorant of prose: it reads JSON, ignores unknown fields, and never calls a model.
  • Audit every draft: tokens, latency, hash. Cap builds so players think.
  • Ship a mock provider so tests and demos run keyless.

6 · Honest limits

  • Models emit invalid JSON sometimes. That is what the validator and the repair pass are for.
  • DNA traits here are descriptive; all behavior lives in rules. Say what your numbers do.
  • This paper is a design note, not legal, safety, or balance advice for other domains.
